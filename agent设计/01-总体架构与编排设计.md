# 01 · 总体架构与编排设计

> 适用对象：架构/开发。阅读前请先看 `00-交付总览.md`。

---

## 1. 设计原则

| 原则 | 含义 | 落地做法 |
|---|---|---|
| **确定性优先** | 能确定的流程不要交给模型自由发挥 | 主链路用固定顺序编排（翻译→识别→改写→检索→生成→校验），只有"判断"环节才用模型决策 |
| **单一职责** | 一个 Agent 只干一件事，输出字段固定 | 7 个 Agent 各自有独立 JSON 输出契约，见 `schemas/` |
| **合规后置强校验** | 合规是闸门不是建议 | 合规校验 Agent 的 `reject` 直接淘汰候选话术，主控无权放行 |
| **证据可追溯** | 每条对外话术能指回来源 | 候选话术必须带 `cited_evidence`，无证据的话术标记 `unsupported` |
| **人机协同** | AI 出候选，人做决定 | 系统不自动发送，永远由客服选用/微调后发出（MVP 阶段） |
| **失败可降级** | 任一子 Agent 挂了，链路不能全废 | 每个 Agent 定义降级输出，见第 7 节 |

## 2. 分层架构

```
┌───────────────────────────────────────────────────────────────────────┐
│ L5 接入层   跨境平台消息（TikTok Shop / Amazon / Temu / 独立站）        │
│             ↓ webhook / 轮询                                           │
├───────────────────────────────────────────────────────────────────────┤
│ L4 应用层   Web 坐席工作台（前端）：会话流 / 候选话术卡片 / 来源引用 /   │
│             一键采纳·微调·忽略 / 转人工 / 满意度回填                    │
├───────────────────────────────────────────────────────────────────────┤
│ L3 编排层   主控 Agent（千帆工作流）：串联、汇总、排序、转人工决策       │
├───────────────────────────────────────────────────────────────────────┤
│ L2 能力层   翻译 | 意图情绪 | 查询改写 | 话术生成 | 合规校验 | 数据闭环 │
│             （6 个子 Agent）                                           │
├───────────────────────────────────────────────────────────────────────┤
│ L1 知识与数据层  5 个 RAG 知识库  |  结构化数据库(13表)  |  合规规则库(可执行)  │
├───────────────────────────────────────────────────────────────────────┤
│ L0 模型层   文心大模型（多语言/生成）+ 抽取型小模型（分类/结构化）      │
└───────────────────────────────────────────────────────────────────────┘
```

## 3. 七个 Agent 职责矩阵

| # | Agent | 输入（关键变量） | 输出（关键字段） | 千帆承载形态建议 | 同步/异步 |
|---|---|---|---|---|---|
| 0 | **主控 Agent** | 全链路变量 | `final` / `escalation` 最终 JSON | 工作流主干 + 大模型汇总节点 | 同步 |
| 1 | **翻译 Agent** | `raw_text`, `source_lang` | `translated_text`, `glossary_hits`, `quality_flag` | LLM 节点（多语言） | 同步 |
| 2 | **意图情绪 Agent** | `translated_text`, 订单/客户画像 | `intent[]`, `emotion`, `urgency`, `risk_flags` | LLM 节点（结构化输出） | 同步 |
| 3 | **查询改写 Agent** | `translated_text`, `intent[]` | `queries[]`, `filters`, `kb_route[]` | LLM 节点（结构化输出） | 同步 |
| — | *（检索执行，非 Agent）* | `queries`, `filters` | `evidence[]`, `coverage` | 知识库检索节点 + 数据库节点（并行） | 同步 |
| 4 | **话术生成 Agent** | `evidence[]`, `intent`, `emotion`, `style` | `candidates[]`（≤3） | LLM 节点（生成 + 结构化输出） | 同步 |
| 5 | **合规校验 Agent** | `candidates[]`, 合规规则库 | `compliance[]`: `pass/revise/reject` | LLM 节点 + 规则前置过滤 + 代码节点 | 同步 |
| 6 | **数据闭环 Agent** | 采纳/修改/忽略/满意度日志 | `optimization_suggestions[]`, `knowledge_gaps[]` | 独立工作流（定时批处理） | **异步** |

**为什么检索不是 Agent**：检索是确定性的数据访问，交给知识库检索节点和数据库节点更稳定、更便宜、可观测。查询改写 Agent 已经承担了"把口语问题变成检索 query"的智能部分。

## 4. 同步主链路编排时序

```
客服工作台/消息网关
   │  { session_id, merchant_id, order_id, raw_text, channel, source_lang }
   ▼
[1] 前置处理（代码节点，非 AI）
     · 语言检测（未提供时）  · PII 脱敏（手机号/邮箱/卡号 → 占位符）
     · 会话窗口取最近 N=6 轮上下文
   ▼
[2] 翻译 Agent ──► translated_text(中文工作语言) + glossary_hits + quality_flag
   │        · 已是中文则直接透传，记录 skipped=true
   ▼
[3] 意图情绪 Agent ──► intent[] / emotion / urgency / risk_flags / need_human_hint
   ▼
[4] 查询改写 Agent ──► queries[]（2~4 条）+ filters{country, platform, category, policy_version}
   │                    + kb_route[]（命中哪几个知识库）
   ▼
[5] 并行检索（同一层级并发，是延迟关键路径）
     ├─ RAG 知识库检索 × kb_route（政策库/产品库/案例库/平台规则库）
     └─ 结构化数据库查询（订单状态、物流轨迹、尺码表、客户历史）
   ▼
   evidence[] + coverage(sufficient | partial | insufficient)
   ▼
[6] 话术生成 Agent ──► candidates[]（≤3 条，每条带 style / text_zh / text_target / cited_evidence）
   ▼
[7] 合规校验 Agent ──► 逐条判定 pass / revise / reject（附 rule_id 与修订文）
   ▼
[8] 主控汇总（大模型节点 + 代码节点）
     · 淘汰 reject，revise 的用修订文
     · 按「意图匹配度 / 情绪适配 / 证据强度 / 合规分」排 recommended
     · 判定 need_human（见第 8 节）
     · 输出最终 JSON
   ▼
[9] 返回客服工作台 ──► 客服选用/微调/忽略 ──► 写入日志
   ▼
[10] 异步：数据闭环 Agent（T+0 事件流 / T+1 批处理）
```

**延迟预算（P95 ≤ 6s）**

| 环节 | 预算 | 说明 |
|---|---|---|
| 前置处理 | 100 ms | 代码节点 |
| 翻译 | 800 ms | 可与意图识别并行优化（见 §9） |
| 意图情绪 | 700 ms | 结构化输出，token 少 |
| 查询改写 | 600 ms | 结构化输出 |
| 并行检索 | 1200 ms | 关键路径，务必并行 |
| 话术生成 | 2000 ms | 最重，3 条候选一次生成 |
| 合规校验 | 700 ms | 规则前置 + 模型兜底 |
| 汇总 | 400 ms | — |
| **合计** | **≈6.5 s** | 超出则先砍候选条数到 2 条 |

> 若 P95 超标，按此顺序优化：① 翻译与意图情绪并行 ② 候选话术降为 2 条 ③ 合规规则前置过滤（命中硬规则的直接拦，不送模型）。

## 5. 异步闭环链路

```
客服操作事件（采纳/修改/忽略） ─┐
客户后续反馈（好评/差评/升级投诉）─┤──► 事件表 qa_logs / feedback
工单结果（退款/换货/关闭）        ─┘
                                    │
                                    ▼
                     数据闭环 Agent（每日 02:00 批处理 + 实时阈值告警）
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
 知识库缺口报告              话术质量报告                 运营优化建议
 · 检索零结果 query 聚类      · 采纳率 / 修改率 / 忽略率    · 需补充的政策条目
 · coverage=insufficient 样本  · 按意图/风格/国别拆解       · 需下线的过时话术
 · 客户反复追问的问题          · 满意度与采纳率相关性        · 术语库新增/修正建议
```

## 7. 异常与降级策略

| 失败节点 | 触发条件 | 降级动作 | 输出影响 |
|---|---|---|---|
| 翻译 Agent | 超时 / 置信度低 | 透传原文 + `quality_flag="low_confidence"` | 意图识别改用原文；工作台提示"翻译不确定，请人工确认" |
| 意图情绪 Agent | 超时 / JSON 解析失败 | 默认 `primary_intent="other"`, `emotion=neutral`, `urgency="high"` | **强制 `need_human=true`**，不自动推荐话术 |
| 查询改写 Agent | 超时 | 用 `translated_text` 原文直接检索 | `queries` 退化为 1 条 |
| 检索 | 全部零结果 | `coverage="insufficient"` | 话术生成只输出通用安抚话术，禁止给政策承诺；`need_human=true` |
| 话术生成 Agent | 超时 / 空结果 | 返回兜底模板（按意图的固定安抚话术） | 标记 `fallback=true` |
| 合规校验 Agent | 超时 / 异常 | **不放行**，全部候选标记 `decision="reject"` 并 `need_human=true` | 安全侧失败必须保守 |
| 任一节点 | 连续失败率 > 5%（5 分钟窗口） | 触发运维告警 + 主控切换为"人工优先"模式 | — |

> **安全铁律**：合规校验节点失败时**一律不放行**。宁可让客服自己写，也不能放一条未校验的话术出去。

## 8. 转人工（Escalation）策略

主控按下表判定 `need_human`，**任一条件命中即转人工**：

| 条件 | 判定依据 | reason 值 |
|---|---|---|
| 紧急度高 | `urgency == "critical"` | `critical_urgency` |
| 情绪失控 | `emotion.intensity >= 4` 且 `polarity == "negative"` | `escalated_emotion` |
| 高价值纠纷 | 订单金额 ≥ 阈值（建议 ¥500 或等值）且 `primary_intent in [refund, quality_defect]` | `high_value_dispute` |
| 检索无据 | `coverage == "insufficient"` | `insufficient_knowledge` |
| 合规全灭 | 所有候选 `decision == "reject"` | `all_candidates_rejected` |
| 平台介入 | `risk_flags` 含 `platform_intervention_risk` 或 `chargeback_risk` | `platform_risk` |
| 法务敏感 | `risk_flags` 含 `legal_risk`（涉及人身伤害、过敏、虚假宣传指控） | `legal_risk` |
| 客户明确要求 | 文本含"转人工/找主管/human/supervisor/encargado" | `customer_request` |
| 连续不采纳 | 同一会话内客服连续 3 次忽略推荐 | `low_acceptance` |

**handoff_packet**（转人工时给人工客服的交接包）必须包含：
- 客户原话 + 中文译文
- 意图/情绪/紧急度判定
- 已检索到的政策依据（带来源与生效日期）
- 已生成但被拒的候选话术及拒因（帮人工避开雷区）
- 建议下一步动作

## 9. 关键工程决策

### 9.1 翻译与意图识别并行
翻译 Agent 输出中文后，意图识别才能跑——但会串行 1.5s。
**优化**：让意图情绪 Agent 同时接收「原文」和「译文」，在译文延迟时先用原文做初步判断，译文到达后复核。MVP 阶段可先串行，压测超标再并行。

### 9.2 中间工作语言统一为中文
所有内部判断（意图、检索、生成）用中文，只在入口（翻译）和出口（回译）处理多语言。理由：知识库、合规规则库、话术模板都是中文，一致性好、成本低。

### 9.3 回译必须用术语库
出口回译走同一套术语库（`data/glossary_zh_en_es_de_fr.csv`），禁止直接机翻。**服装术语机翻是投诉重灾区**（如"起球"翻成 "ball"、"色差" 翻成 "color difference" 客户看不懂）。

### 9.4 多轮上下文管理
- 会话窗口取最近 6 轮，超长则摘要压缩。
- 意图识别以**本轮 + 前 2 轮**为准；客户中途换话题（如从物流转退款）时以本轮为准并重置 `primary_intent`。
- 每轮都重新走完整链路，**不做跨轮的话术缓存**（合规要求每轮都校验）。

### 9.5 幂等与去重
`trace_id` 唯一；同一 `session_id` + 相同 `raw_text` 在 30s 内重复进入时，直接返回缓存结果，避免重复扣费。

## 10. 与千帆的承载对应（概览）

| 本设计概念 | 千帆对应（名称以控制台为准） |
|---|---|
| 主控 Agent | 工作流应用主干 + 大模型节点（汇总）+ 代码节点（淘汰/排序） |
| 6 个子 Agent | 工作流中的大模型节点（配结构化输出）；如需独立可调试可发布为组件/子工作流 |
| 检索执行 | 知识库检索节点（并行多路）+ 数据库节点 |
| 合规规则库 | 数据库节点（结构化规则表）+ 代码节点（正则硬拦截）+ 大模型节点（语义判定） |
| 会话状态 | 应用会话变量 / 外部 Redis（自建工作台侧） |
| 发布接入 | 发布为 API，由自建 Web 坐席工作台调用 |

> 详细节点级搭建步骤见 `04-千帆AppBuilder搭建实施手册.md`。平台官方文档入口已在手册中列出。
