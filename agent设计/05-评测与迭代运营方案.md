# 05 · 评测与迭代运营方案

> 没有评测的 AI 产品只能靠"感觉好像变好了"来迭代。
> 这份文档定义：**测什么、怎么测、多少算达标、不达标怎么办。**

---

## 1. 评测体系的三层结构

| 层 | 测什么 | 频率 | 谁负责 |
|---|---|---|---|
| **L1 单元评测** | 单个 Agent 的输出质量（意图准确率、翻译术语命中率…） | 每次改提示词/换模型后必跑 | AI 开发 |
| **L2 链路评测** | 端到端最终 JSON 的正确性与合规性 | 每次发版必跑 | AI 开发 |
| **L3 业务评测** | 客服采纳率、满意度、纠纷率下降（申报书承诺的业务价值） | 每周 | 产品运营 |

**三层缺一不可**：L1 好但 L2 差通常是编排问题；L1/L2 好但 L3 差通常是产品形态问题（比如话术太长客服懒得用）。

---

## 2. 评测集构建

### 2.1 规模与来源

| 来源 | 建议占比 | 说明 |
|---|---|---|
| 真实商户历史对话（脱敏） | 50% | 最贴近真实分布，试点商户上线后持续补充 |
| 模拟构造场景 | 30% | 覆盖低频但高风险的场景（法律威胁、儿童安全、平台介入） |
| 人工对抗样本 | 20% | 专门设计的"诱导违规"样本，验证合规闸门 |

**MVP 期规模建议 150~300 条**，能覆盖全部 14 个意图标签 × 5 个主要国家 × 3 个主要平台。
规模不必大，**覆盖率比数量重要**。

### 2.2 评测集分层（必须保证每一层都有足够样本）

| 分层维度 | 取值 | 每层最少样本 |
|---|---|---|
| 意图 | 14 个标签 | 各 8 条 |
| 国家 | DE / ES / FR / US / GB + UNKNOWN | 各 20 条 |
| 平台 | tiktok_shop / amazon / temu | 各 20 条 |
| 紧急度 | low / medium / high / critical | 各 15 条（critical 建议 30 条） |
| 合规预期 | pass / revise / reject | 各 30 条 |
| 语言 | en / es / de / fr / zh | 各 20 条 |

模板见 `data/eval_set_template.csv`（含 26 条已标注样本，其中 6 条为诱导型对抗样本），按该模板扩充即可。

> **两层测试不要混用**（这是一个容易犯的设计错误）：
> - `eval_set_template.csv` 测的是**端到端链路质量** —— 这里 `expected_compliance_decision` 是
>   "理想情况下最终话术应有的判定"，所以对抗样本的期望值是 `pass`（考察生成环节会不会上钩）。
> - `data/compliance_unit_test.csv` 测的是**合规闸门的拦截能力** —— 直接喂入**故意违规的话术文本**，
>   验证是否被正确 reject/revise。这一层不经过生成环节，是纯单元测试。
>
> 想验证"合规闸门拦不拦得住"，用后者；想验证"AI 会不会自己写出违规话术"，用前者。

### 2.3 标注要求

每条评测样本必须标注：

| 字段 | 说明 |
|---|---|
| `expected_primary_intent` | 期望主意图 |
| `expected_urgency` | 期望紧急度（critical 宁可多标，漏判代价高） |
| `expected_need_human` | 期望是否转人工 |
| `expected_compliance_decision` | 期望合规判定 |
| `expected_violation_rules` | 若应 reject/revise，期望命中的 rule_id |
| `expected_must_include` | 话术必须包含的要点（如"运费由商家承担"） |
| `expected_must_not_include` | 话术绝对不能出现的表述 |

**双人标注 + 分歧仲裁**：意图与合规标注必须两人独立标注，分歧由第三人或产品负责人仲裁。
标注一致性（Cohen's Kappa）低于 0.7 说明标注规范本身有歧义，要先修规范再评测。

## 3. 各 Agent 的评测指标与达标线

| Agent | 核心指标 | 达标线 | 补充指标 |
|---|---|---|---|
| **翻译 Agent** | 术语命中准确率 | ≥ 95% | 关键信息（金额/尺码/订单号）保留率 = 100% |
| | 情绪保真度（人工 1-5 分） | ≥ 4.0 | 回译可用性 ≥ 4.0 |
| **意图情绪 Agent** | `primary_intent` 准确率 | ≥ 90% | 全部意图标签的 macro-F1 ≥ 0.85 |
| | `urgency` 分级准确率 | ≥ 85% | **`critical` 召回率 ≥ 95%**（漏判代价最高） |
| | 情绪强度 ±1 一致率 | ≥ 85% | — |
| **查询改写 Agent** | 检索 Recall@5 | ≥ 85% | 零结果率 ≤ 10% |
| | `filters` 关键字段填充率 | ≥ 95% | `country` 错误率 ≤ 2% |
| **话术生成 Agent** | 意图匹配率（人工 ≥4/5） | ≥ 85% | `cited_evidence` 非空率 ≥ 90% |
| | 首次合规 pass 率 | ≥ 70% | 风格互异率 = 100% |
| | 长度合规率 | = 100% | — |
| **合规校验 Agent** | 违规召回率 | ≥ 95% | — |
| | 误杀率 | ≤ 5% | `revise` 后复检 pass 率 ≥ 95% |
| | `reject` 可归因率 | = 100% | 所有 reject 都有 rule_id |
| **主控 Agent** | 输出 Schema 校验通过率 | = 100% | `degraded_nodes` 触发率 ≤ 2% |
| | `need_human` 判定一致率 | ≥ 90% | `reject` 话术零泄漏 = 100% |
| **数据闭环 Agent** | 建议可执行率（人工评估） | ≥ 80% | 每周 P0 建议完成率 ≥ 70% |
| | 建议有证据率 | = 100% | — |

### 3.1 三条"零容忍"红线

以下三项任何一次不达标即为**阻断性缺陷**，必须立即修复，不允许带病上线：

| 红线 | 定义 | 验证方式 |
|---|---|---|
| **合规零泄漏** | 最终 JSON 中不出现任何被 reject 的话术文本 | 抽样 200 条全链路输出，程序化比对 |
| **隐私零泄露** | 输出与日志中不出现明文 PII | 正则扫描全部输出字段 |
| **Schema 零失败** | 最终 JSON 100% 通过 Schema 校验 | 批量跑评测集，自动校验 |

## 4. 北极星指标与监控看板

主链路灰度上线后，固定监控这 6 个指标（数据来自 `qa_logs` / `feedback`）：

| 指标 | 口径 | 健康区间 | 异常含义 |
|---|---|---|---|
| **采纳率** | (直接采纳 + 微调采纳) / 总推荐 | ≥ 60% | 低于 40% 说明话术不能用 |
| **忽略率** | 客服未使用任何候选 / 总推荐 | ≤ 15% | 偏高说明推荐不相关 |
| **满意度** | 好评 / 有反馈数 | ≥ 75% | — |
| **合规 reject 率** | 全部候选被 reject 的会话 / 总会话 | ≤ 5% | 偏高说明生成环节在系统性踩雷 |
| **覆盖不足率** | `coverage = insufficient` / 总会话 | ≤ 10% | 偏高说明知识库缺口大 |
| **P95 延迟** | 端到端 | ≤ 6s | 偏高先查检索是否并行 |

**看板必须按「意图 × 风格 × 国家 × 平台」四个维度可下钻**，
否则只知道"变差了"却不知道"哪里变差了"。

## 5. 自动化评测流程

```
改动提示词 / 换模型 / 改知识库
        │
        ▼
[1] 跑评测集（150~300 条）──────────► L1 各 Agent 指标
        │
        ▼
[2] 与基准版本对比，生成 diff 报告
        │   · 哪些指标提升、哪些下降
        │   · 新增回归的样本清单（带 trace_id）
        ▼
[3] 自动执行三条红线检查
        │   · 合规零泄漏 / 隐私零泄露 / Schema 零失败
        │   任一失败 → 阻断发布
        ▼
[4] 人工抽查（每次 30 条，覆盖变化最大的分层）
        │
        ▼
[5] 通过 → 进入灰度；不通过 → 回到改动
```

**建议把 [1]~[3] 做成一键脚本**，纳入发版流程。
没有自动化的评测等于不会被执行——这是 AI 项目最常见的失败原因。

## 6. 人工评测规范

### 6.1 评分卡（话术质量，1-5 分）

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| **意图匹配** | 答非所问 | 大致相关 | 精准回应当前诉求 |
| **情绪适配** | 语气激怒或冷淡 | 中性可接受 | 语气贴合客户情绪状态 |
| **可执行性** | 客户看了不知道要做什么 | 有模糊的下一步 | 有明确可执行的下一步 |
| **专业性** | 有明显错误或外行表述 | 无误但泛泛 | 术语准确、依据清晰 |
| **可直接使用** | 需完全重写 | 需小幅修改 | 可一键复制发送 |

**判定"可直接使用"的口径**：客服**不需要改动任何字**就能发送，计 5 分；
改动 1~2 处措辞计 4 分；需要重写超过一半计 1~2 分。

### 6.2 盲评与一致性

- 评测时**隐藏模型版本与提示词版本**，避免主观偏向。
- 关键版本采用**双人盲评**，分差 ≥ 2 分的样本进入仲裁。
- 定期用固定的 20 条"锚点样本"校准评分人漂移。

## 7. Bad Case 闭环

```
发现 bad case
     │
     ├─►【归类】哪一层的问题？
     │     翻译 / 意图 / 改写 / 检索 / 生成 / 合规 / 编排 / 产品形态
     │
     ├─►【定位】看 trace_id 链路日志，找到第一个出错的节点
     │
     ├─►【修复】
     │     · 提示词问题     → 改 prompts/ 对应文件 + 补反例
     │     · 知识库缺口     → 补文档 / 补条目（走 03 的更新 SOP）
     │     · 规则缺口       → 补 compliance_rules（高频的顺带补正则）
     │     · 数据问题       → 修 filters / 数据质量
     │     · 编排问题       → 改工作流连线或降级策略
     │
     ├─►【回归】把该样本加进评测集，防止再次退化
     │
     └─►【验证】下一版本评测时确认该样本通过
```

**关键要求**：每个 bad case 都必须**沉淀为一条评测样本**。
评测集只增不减，它是这个产品最值钱的资产之一。

## 8. 灰度上线与 A/B

| 阶段 | 范围 | 目标 | 退出条件 |
|---|---|---|---|
| **内部验证** | 团队自用 | 链路跑通 | 8 个边界用例全通过 + 三条红线达标 |
| **影子模式** | 3~5 家试点商户 | **只生成不发送**，对比 AI 推荐与客服实际发送的差异 | 采纳率 ≥ 50%，无合规泄漏 |
| **辅助模式** | 3~5 家试点商户 | 客服可选用，人工确认后发送 | 采纳率 ≥ 60%，满意度 ≥ 75% |
| **规模推广** | 20~30 家 | 覆盖更多品类与国家 | 稳定运行 2 周无 P0 |

**为什么先做影子模式**：它能在零风险的情况下暴露话术质量问题，
并**免费获得一批真实标注数据**（AI 推荐 vs 客服实际发送的差异就是最有价值的 bad case 来源）。

### A/B 测试注意

- 同一商户内分流，避免商户间差异污染结论。
- 核心指标看**采纳率**与**满意度**，不要只看延迟。
- 样本量不足时不要下结论（建议每组 ≥ 200 个会话）。

## 9. 里程碑（对应申报书 6.3 阶段性落地路径）

### MVP 验证期（1-3 个月）

| 周次 | 交付 |
|---|---|
| W1-W2 | 数据准备：种子数据入库，法务完成政策与规则确认 |
| W3-W4 | 5 个知识库建成，7 个 Agent 节点搭建完成 |
| W5-W6 | 工作流串联 + 降级分支 + 边界用例通过 |
| W7-W8 | 评测集构建（150 条），跑通自动化评测 |
| W9-W10 | 3~5 家试点商户影子模式 |
| W11-W12 | 转辅助模式，收敛首批 bad case，形成落地案例 |

**退出标准**：采纳率 ≥ 60%，合规 reject 率 ≤ 5%，覆盖不足率 ≤ 10%。

### 规模迭代期（3-6 个月）

- 拓展至 20~30 家商户
- 完善多语言（补齐小语种）与合规体系（补齐国家）
- 数据闭环 Agent 稳定运行，每周产出可执行建议
- 完成产品标准化打磨

### 全面推广期（6-12 个月）

- 标准化 SaaS 产品成型
- 依托产业园与政府平台规模化推广
- 指标目标（对应申报书业务价值）：售后满意度提升、纠纷率下降

## 10. 团队分工与运营 SOP

| 角色 | 人数 | 评测与运营职责 |
|---|---|---|
| **AI 开发工程师** | 1-2 | 跑自动化评测、改提示词、修 bad case、维护 Schema 一致性 |
| **前后端开发工程师** | 1 | 工作台交互（6 个交互）、日志埋点、数据管道、脱敏流程 |
| **产品运营专员** | 1 | 标注评测集、人工盲评、术语库维护、建议清单跟踪、商户对接 |
| **跨境业务顾问** | 1（兼职） | 政策库内容、案例库"可复用经验"、法务确认配合 |

### 每周固定节奏（建议）

| 时间 | 事项 | 产出 |
|---|---|---|
| 周一 | 数据闭环 Agent 周报推送 | 优化建议清单（≤10 条） |
| 周一 | 上周 P0 建议完成情况回顾 | 完成率 |
| 周三 | 人工盲评 30 条 | 评分卡 + bad case 清单 |
| 周五 | 发版评测（若本周有改动） | diff 报告 + 红线检查结果 |
| 每周 | 术语库更新 | 新增/修正条目 |
| 每月 | 合规规则库复核 | 规则增删改记录 |
| 每 180 天 | 政策库全量复核（法务） | `verified_by` 更新 |

## 11. 风险与应对（对应申报书第 8 节）

| 申报书识别的风险 | 本方案的具体应对 | 验证方式 |
|---|---|---|
| **商户优质历史对话数据稀缺** | 初期用种子数据（政策/行业标准/平台规则）搭基础库；用模拟场景对话补评测集；试点商户上线后优先沉淀影子模式的对比数据 | 评测集规模从 150 条持续增长；`case_kb` 条目周增 |
| **小语种翻译、行业术语精准度不足** | 术语库确定性替换优先于模型；术语命中率作为翻译 Agent 的首要指标；数据闭环 Agent 每周给术语新增建议 | 术语命中率 ≥ 95%；一周内 `glossary_miss` 样本持续下降 |
| **中小商户数字化接受度偏低** | 先做影子模式降低心理门槛；用试点商户的采纳率与纠纷率下降数据做成果背书；界面只保留"复制/微调/发送"三个动作 | 试点商户转辅助模式的转化率 |
| **市面同类 AI 客服竞品较多** | 壁垒在数据不在模型：汉派服装垂直知识库 + 各国合规规则库 + 案例经验库三层数据；这三层是通用工具无法复刻的 | 覆盖不足率 ≤ 10%（通用工具在垂直场景会显著更高） |

---

## 12. 一句话总结

> **评测集是这个产品最值钱的资产，数据闭环是这个产品唯一的护城河。**
> 模型会过时、平台会变，但只要评测集在增长、术语库和政策库在沉淀，
> 换任何底座模型都能快速恢复能力。
