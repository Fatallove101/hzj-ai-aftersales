# 03 · 知识库与数据层设计

> 这一层是**产品壁垒所在**：申报书里的"完全适配本土商户经营场景，解决通用 AI 工具不专业、不贴合、不落地的问题"，
> 靠的就是这里的数据。模型可以换，数据不能没有。

---

## 1. 三层知识架构

跨境售后的答案由三种性质完全不同的知识决定，必须**分开存放、分开检索、分开维护**：

| 层 | 存什么 | 形态 | 谁维护 | 为什么必须是这种形态 |
|---|---|---|---|---|
| **L1 语义知识层** | 政策条文、平台规则、产品说明、历史案例、合规范例 | **RAG 知识库 ×5**（向量检索） | 业务顾问 / 运营 | 内容长、表述活、需要语义匹配 |
| **L2 结构化数据层** | 订单、物流、商品、尺码、客户画像、商户、日志 | **关系数据库**（精确查询） | 开发 / 运营 | 需要精确、可聚合、可关联，不能靠语义猜 |
| **L3 可执行规则层** | 合规规则、术语映射 | **规则表 + 正则**（确定性匹配） | 法务 / 运营 | **违规判定不能靠概率**，必须可复现、可审计 |

**关键设计判断**：把"合规"放进 L3 而不是 L1。
如果只把合规做成知识库文档，模型可能检索到了却不遵守；把规则做成可执行的正则与结构化字段，
才能做到"命中即拦截"，且每次拦截都能说出命中了哪一条规则。

## 2. L1 · RAG 知识库分库设计

### 2.0 分库原则

不建一个大库，而是按**检索意图**分库。理由：
- 不同库的切片粒度、元数据、更新频率完全不同；
- 分库后可做**路由检索**（查询改写 Agent 输出 `kb_route`），减少无效召回与 token 消耗；
- 分库便于按库评估覆盖率，知道"是哪个知识面不足"。

### 2.1 五个知识库

---

#### KB1 `policy_kb` · 各国跨境售后政策库

| 项 | 内容 |
|---|---|
| **用途** | 回答"这个国家法律怎么规定的"——退货期限、运费承担、瑕疵救济顺位、告知义务 |
| **数据来源** | `data/policy_index.csv` 扩写；各国官方法条原文与官方指南；行业协会解读 |
| **文档粒度** | **一条政策 = 一篇文档**（不要合并成一个国家的长文档，否则切片会串味） |
| **切片策略** | 按条款切，每片 300~500 字，**不允许跨越条款边界**；条款编号保留在片首 |
| **必须的元数据** | `country`, `region`, `policy_name`, `doc_id`, `effective_date`, `expiry_date`, `source_url`, `status` |
| **检索策略** | 混合检索（向量 + 关键词）；`top_k = 5`；分数阈值 0.55；对 `effective_date` 做**硬过滤** |
| **时效要求** | **最高**。政策条目必须有 `effective_date`，检索时强制 `effective_date <= today` |
| **更新频率** | 每 180 天全量复核；政策变动即时更新 |

**文档模板**

```markdown
# {国家/地区} · {政策名称}
- doc_id: {doc_id}
- 适用国家: {country}    地区: {region}
- 生效日期: {effective_date}    失效日期: {expiry_date 或 NA}
- 来源: {source_url}
- 适用平台: {applies_platform}

## 核心口径
{一句话说清这条政策对服装售后的实际影响}

## 条款要点
1. {要点1，含条款编号}
2. {要点2}

## 对商家的义务
- {义务1}
- {义务2}

## 对消费者的权利
- {权利1}

## 服装售后场景应用
- 场景：{如"客户收到有色差的连衣裙要求退款"}
  - 正确答案：{该怎么处理}
  - 禁止表述：{不能说什么}

## 常见误区
- {误区1}
```

> **"服装售后场景应用"这一节是灵魂**。法条原文模型读了也不会用，
> 必须由业务顾问把它翻译成"遇到 X 场景该怎么说"。

---

#### KB2 `platform_rule_kb` · 电商平台规则库

| 项 | 内容 |
|---|---|
| **用途** | 回答"这个平台允许我怎么做"——退货窗口、争议流程、责任判定、处罚规则 |
| **数据来源** | 各平台卖家中心官方规则页、平台公告、卖家社群实操经验（需标注可信度） |
| **文档粒度** | **一个平台 × 一个规则主题 = 一篇文档** |
| **切片策略** | 按规则条目切，300~600 字；流程类内容保留完整步骤不切断 |
| **必须的元数据** | `platform`, `country_site`, `rule_topic`, `doc_id`, `effective_date`, `source_url`, `reliability`（official / community） |
| **检索策略** | 向量检索；`top_k = 5`；阈值 0.55；按 `platform` 硬过滤 |
| **更新频率** | 每月检查一次规则页；平台大促前必查（规则常在大促前调整） |

**规则主题建议清单**：退货与退款政策 / 争议与仲裁流程 / 商品描述规范 / 评价规则 / 卖家违规与处罚 / 物流时效要求 / 特殊品类（童装）要求。

> `reliability` 字段很重要：`community` 来源的实操经验**不得**作为对外政策依据，
> 只能作为内部参考。话术生成时只能引用 `official` 来源。

---

#### KB3 `product_kb` · 汉派服装产品与质检知识库

| 项 | 内容 |
|---|---|
| **用途** | 回答"这件衣服是什么、怎么用、什么标准"——面料成分、尺码标准、洗涤保养、质检要求 |
| **数据来源** | 商户产品手册、吊牌信息、供应商资料、国标/欧标质检标准（如 EN 14682 童装绳带、CPSIA） |
| **文档粒度** | **一个品类一份知识文档** + **一个 SKU 一条结构化记录**（SKU 走数据库不走 RAG） |
| **切片策略** | 按"品类 × 知识维度"切（面料/尺码/保养/质检各成片），400~600 字 |
| **必须的元数据** | `category`, `fabric`, `standard_code`, `doc_id`, `source`, `effective_date` |
| **检索策略** | 向量检索；`top_k = 4`；阈值 0.5；按 `category` 硬过滤 |
| **更新频率** | 新品上线同步；季度复核 |

**为什么要按品类切**：客户问"羊毛衫会缩水吗"，命中"针织衫保养"文档比命中"连衣裙面料"文档有用得多。
品类是最强的检索信号之一，必须做成硬过滤。

> **尺码表不进 RAG，进数据库**。尺码是精确匹配场景（"EU38 的胸围是多少"），
> 语义检索会给出一个"大概相关"的答案，这在尺码场景等于错误答案。

---

#### KB4 `case_kb` · 优质售后案例库

| 项 | 内容 |
|---|---|
| **用途** | 给话术生成提供"同类场景别人是怎么处理的、效果如何"的经验参考 |
| **数据来源** | 历史成功对话（**脱敏后**）、客服优秀案例沉淀、试点商户真实工单 |
| **文档粒度** | **一个案例 = 一篇文档**（一次完整的售后处理） |
| **切片策略** | **不切片**。案例必须完整保留"客户问题 → 处理动作 → 客户反应"的全过程 |
| **必须的元数据** | `primary_intent`, `country`, `platform`, `category`, `outcome`（resolved / escalated / refunded）, `satisfaction`, `doc_id`, `anonymized`（必须为 true） |
| **检索策略** | 向量检索；`top_k = 3`；阈值 0.6（案例参考要准，宁少勿滥） |
| **更新频率** | 每周从高采纳高满意样本中筛选新增 |

**脱敏要求（强制）**：入库前必须移除客户昵称、订单号、联系方式、地址、商品链接。
保留脱敏后可识别的业务要素（国家、平台、品类、意图）。
`anonymized` 字段为 false 的文档**不得入库**。

**案例文档模板**

```markdown
# 案例：{一句话场景描述}
- doc_id: {doc_id}    primary_intent: {intent}    country: {country}
- platform: {platform}    category: {category}
- outcome: {resolved / refunded / exchanged / escalated}
- satisfaction: {1-5}    anonymized: true

## 客户问题（脱敏后原文 + 中文译文）
{原文}
{译文}

## 处理过程
1. {客服第一轮回复要点}
2. {客户反应}
3. {客服第二轮回复要点}

## 结果
{最终如何解决，客户如何反馈}

## 可复用的经验
- {经验1：这类客户最在意什么}
- {经验2：哪个表述有效}
- {经验3：哪个表述要避开}
```

> "可复用的经验"这一节决定案例库的价值。没有这一节，案例库就只是聊天记录。

#### KB5 `compliance_kb` · 合规表述规范库

| 项 | 内容 |
|---|---|
| **用途** | 给话术生成提供"合规的说法长什么样"的正面范例，与 `compliance_rules` 的负面清单互补 |
| **数据来源** | 法务审核过的话术模板、平台官方合规范例、各国法定告知文本（如欧盟撤回权告知模板） |
| **文档粒度** | **一个场景 × 一种规范 = 一篇文档** |
| **切片策略** | 按段落切，200~400 字；告知类文本（如法定模板）整篇不切 |
| **必须的元数据** | `country`, `scenario`, `disclosure_type`（法定义务告知 / 表述规范 / 禁用词替代方案）, `doc_id`, `effective_date` |
| **检索策略** | 向量检索；`top_k = 3`；阈值 0.6 |
| **更新频率** | 与 `compliance_rules` 同步更新 |

**典型内容**：
- 欧盟 14 天无理由退货权的**标准告知话术**（各国语言版本）
- 德国 Widerrufsrecht 告知模板
- 禁用词的标准替代方案（"保证退款" → "我们将按平台流程为您处理退款"）
- 关税/清关责任说明的合规表述

> 这个库的作用是让**话术生成 Agent 更容易一次写对**，从而减少合规校验 Agent 的 revise 次数。
> 上线初期 `pass` 率低是正常的，把 revise 高频点沉淀进这个库，pass 率会持续上升。

---

### 2.2 五个知识库的检索参数汇总

| 知识库 | top_k | 分数阈值 | 元数据硬过滤 | 切片长度 | 时效过滤 |
|---|---|---|---|---|---|
| `policy_kb` | 5 | 0.55 | country / region | 300~500 字 | **强制** |
| `platform_rule_kb` | 5 | 0.55 | platform | 300~600 字 | 建议 |
| `product_kb` | 4 | 0.50 | category | 400~600 字 | 否 |
| `case_kb` | 3 | 0.60 | country / platform / category | 不切片 | 否 |
| `compliance_kb` | 3 | 0.60 | country / scenario | 200~400 字 | 建议 |

**合并策略**：各路召回结果合并后按 `score` 排序，取 Top 8 作为 `evidence` 喂给话术生成 Agent。
每路至少保留 1 条（避免某一路被完全压制），最多保留 3 条（避免单一库刷屏）。

### 2.3 检索覆盖度 coverage 的判定

这是主控决定要不要转人工的关键字段，必须有明确定义：

| coverage | 判定条件 |
|---|---|
| `sufficient` | 至少有 1 条 `policy_kb` 或 `platform_rule_kb` 命中（score ≥ 0.55），且 `filters.country` 不为 UNKNOWN |
| `partial` | 仅 `case_kb` / `product_kb` 命中，或命中分数在 0.4~0.55 之间 |
| `insufficient` | 全部零结果，或 `filters.country == "UNKNOWN"`（**国家未知时一律视为无据**） |

> `filters.country == "UNKNOWN"` 判为 `insufficient` 是刻意的保守设计：
> 不知道该客户在哪个国家，就不可能给出正确的政策答案，此时唯一安全的动作是转人工。

## 3. L2 · 结构化数据库设计

完整的建表 DDL 见 `data/db_schema.sql`（13 张表）。这里只说设计意图与几个关键决策。

### 3.1 表分组

| 分组 | 表 | 服务于哪个 Agent |
|---|---|---|
| 业务主数据 | `merchants`, `products`, `size_charts` | 查询改写（品类兜底）、话术生成（产品参数） |
| 交易与画像 | `orders`, `shipments`, `customers`, `after_sales_cases` | 意图情绪（高价值纠纷判定）、主控（转人工）、话术生成 |
| 术语 | `glossary` | 翻译 Agent、话术生成 Agent |
| 合规 | `compliance_rules`, `policy_index` | 合规校验 Agent、查询改写 Agent |
| 闭环 | `qa_logs`, `feedback`, `optimization_actions` | 数据闭环 Agent |

### 3.2 三个关键设计决策

**① `policy_index` 与 `policy_kb` 是同一份数据的两种形态**
- `policy_index` 表：用于**精确过滤与时效校验**（`effective_date <= CURDATE()`）
- `policy_kb` 知识库：用于**语义召回**（找到"哪条政策和客户问题相关"）

两者必须用同一个 `doc_id` 对齐。检索流程是：先在库里语义召回候选 doc_id，
再用 `policy_index` 表校验其时效性与适用范围。**只有语义召回的合规是危险的。**

**② `customers` 表严禁存储支付敏感信息**
售后场景不需要银行卡、证件号。表里只有国家、语言、VIP 等级、订单数、争议次数。
这是设计约束，不是"暂时没加"。

**③ `qa_logs.customer_text_masked` 是脱敏后的文本**
PII 在**写入前**替换为占位符（`[PHONE]`、`[EMAIL]`、`[ADDR]`、`[ORDER]`）。
数据闭环 Agent 只读脱敏后的数据，从源头保证它不可能泄露客户信息。

### 3.3 数据质量校验（建议做成定时任务）

| 检查项 | 频率 | 失败处理 |
|---|---|---|
| `orders.country` 为空占比 > 5% | 每日 | 告警（国家缺失直接导致 coverage 降级） |
| `policy_index` 中 `effective_date` 超过 `review_cycle_days` 未复核 | 每日 | 推送给法务 |
| `compliance_rules` 中 `status = 'seed'` 的条目占比 > 0 | 每日 | 提醒法务确认（上线前必须清零） |
| `glossary` 中 `status = 'deprecated'` 仍被检索命中 | 每周 | 修正检索过滤条件 |
| `qa_logs` 中出现疑似未脱敏的手机号/邮箱 | 每日 | **P0 告警**，排查脱敏环节 |

## 4. L3 · 可执行合规规则库

### 4.1 双层校验机制

```
候选话术
   │
   ├──►【第一层：正则硬拦截】compliance_rules.pattern
   │      · 命中 severity = block  →  直接 reject，不进模型
   │      · 命中 severity = revise →  标记待修订，继续进模型
   │      · 成本≈0，100% 可复现
   │
   └──►【第二层：模型语义判定】
          · 处理正则覆盖不到的隐性风险（归因结论、语气威胁、变相站外引流）
          · 判断跨境正向义务是否缺失（欧盟 14 天告知）
          · 输出 span / reason / suggestion / revised_text
```

**为什么必须双层**：正则能 100% 抓住"加微信""100%""保证3天到账"，但抓不住
"我们已经确认是运输造成的"。模型能抓住后者，但会漏掉新出现的违禁词变体。
两层互补，且正则层的结论**模型必须采纳，不得推翻**。

### 4.2 规则表字段说明（`data/compliance_rules.csv`）

| 字段 | 作用 |
|---|---|
| `rule_id` | 规则编号，所有 reject 都必须能归因到某个 rule_id，便于审计 |
| `category` | 六类：promise / privacy / platform_rule / advertising / discrimination / cross_border |
| `severity` | `block` 直接淘汰；`revise` 可改写放行；`warn` 仅提示 |
| `pattern` | 正则表达式，供代码节点执行 |
| `match_mode` | **`violation`**：pattern 命中即构成违规；**`obligation`**：pattern 只表示"规则适用"，是否违规必须由模型判断 |
| `applies_country` | 适用国家，`|` 分隔；`SCOPE_GLOBAL` 表示全球 |
| `revise_hint` | 给模型的修订方向提示 |

#### `match_mode` 为什么必须有（一个真实踩坑记录）

最初把「欧盟订单须体现 14 天无理由退货权」（R018）和「德国订单须提示撤回权」（R019）
也写成了 `violation` 型规则，pattern 是 `(退货|退款|devolución|retour|Rücksendung)`。

结果是：**任何提到"退货/退款"的合规话术都会被正则命中并判 revise**，包括完全正确的话术。
用 `data/compliance_unit_test.csv` 做回归时立刻暴露了这个问题——
一条完全合规的欧盟退款话术（T021）被误判为 revise，**误杀率 100%**。

根本原因：R018/R019 是**正向义务**（"必须说了什么"），而不是**违规模式**（"不能说什么"）。
两者的检测逻辑完全不同：

| 类型 | 检测逻辑 | 能否用正则 |
|---|---|---|
| `violation` | 文本中**出现**某模式 → 违规 | ✅ 可以，正则 100% 可靠 |
| `obligation` | 文本中**缺少**某内容 → 违规 | ❌ 不可以，只能由模型判断"该说的说了没有" |

**工程后果**：
- 代码节点的正则硬拦截**只跑 `match_mode = 'violation'` 的规则**；
- `obligation` 类规则的 `pattern` 只用来判断"这条规则是否适用于本条话术"，
  实际判定由合规校验 Agent 的模型层完成（`cross_border_check.missing_disclosures` 字段承载）。

> **这条经验值得推广**：任何"必须有 X"的规则都不能用正则白名单的方式实现。
> 白名单式正则会退化成"提到关键词就报错"，是误杀率的主要来源。

### 4.3 规则的演进机制

```
合规校验 Agent 判定 revise / reject
        │
        ▼
数据闭环 Agent 聚合高频模式（compliance_feedback.top_rejected_rules）
        │
        ├──► 高频 reject 模式  ──►  提炼正则补进 compliance_rules.pattern（前端拦截，省模型调用）
        ├──► 高频 revise 改写点 ──►  补进 prompts/04 的禁止清单 + compliance_kb 的正面对照
        └──► 灰区样本（confidence < 0.6）──► 人工复核 → 补规则或补示例
```

**规则库的版本管理要求**：
- 每次变更记录 `verified_by` 与 `verified_date`；
- 保留历史版本，以便回答"当时这条话术依据的是哪一版规则"；
- `status` 字段控制生效（`seed` 未核实 / `active` 已核实 / `deprecated` 已废止）。

> ⚠️ 当前 `data/compliance_rules.csv` 的 25 条规则全部为 `seed` 状态，
> 需法务逐条确认后改为 `active`。确认前建议检索与生成环节只引用 `active` 条目。

## 7. 隐私与合规数据处理要求

1. **最小必要**：只采集售后处理必需的数据。不采集银行卡、证件号、精确位置。
2. **入库即脱敏**：`raw_text` 在写入日志前完成 PII 占位符化，脱敏后的字段才允许被 AI 处理。
3. **案例脱敏**：`case_kb` 的每条案例必须有 `anonymized: true` 标记，且经过人工抽查。
4. **聚合输出**：数据闭环 Agent 的输出只允许聚合结果与脱敏片段，不得输出可反查个人的信息。
5. **数据留存**：原始对话建议留存不超过 12 个月，到期删除或匿名化（以商户协议约定为准）。
6. **跨境数据**：客户数据出境需符合《个人信息保护法》相关要求，建议优先使用境内节点存储，
   并对出境数据做匿名化处理。
7. **审计留痕**：合规拦截记录（rule_id + span）必须留存，用于应对平台质询与内部复盘。

> 本节为工程与产品层面的设计约束，具体合规要求须以法务意见为准。
