# 跨境销售 AI 话术助手 · 坐席副驾（hzj-ai-aftersales）

> ⚠️ **定位（很重要，别理解错）**：本工具**不是「AI 客服」**，也**不是**"AI 答不了就转人工"。
>
> 真实业务链路是：**别的 AI 客服先接待 → 解决不了转人工 → 人工坐席用本工具生成话术 → 人工确认后回复客户**。
>
> 所以：**我们的用户是坐在工位上的人工客服**，我们的产出是**给人工用的话术建议**，
> 我们**永远不直接面向终端客户发消息**。
>
> 这带来三个具体后果：
> 1. 界面上没有"建议转人工"，只有「**⚠ 高风险案件 · 回复前请核实**」
> 2. 对话里会混着**前面 AI 客服说过的话**，必须能分清（否则人工会和 AI 自相矛盾）
> 3. **"符合当地政策"是核心卖点**，政策依据面板和分析面板同级突出

---

> 场景：你是某个跨境电商卖家的销售客服坐席。客户的消息可能来自任何一个环节 ——
> 售前问尺码材质、售中催发货改地址、售后退换货要说法；也可能前面已经由 AI 客服接待过一轮、
> 没解决**已经转到了你手上**。你不知道该怎么回才既得体、又符合当地法规。
> 这个工具**自动读取屏幕上的对话**，识别客户意图/情绪/风险，检索该国政策与术语库，
> 生成中外双语候选话术（带合规校验和来源引用），你**点一下插入**就能发出去。

> **不限定品类**：知识库、合规规则库、术语库都是可替换的 CSV 数据文件；
> 术语库以服装类目起家，换品类只需按同一格式扩充。

## 技能系统（hzj-ai-aftersales/skills/）

**技能 = 一个 Markdown 文件**，YAML frontmatter 放元数据，正文放指令。可增删，加载器零依赖。

### 格式（照着现有 6 个改即可）

```yaml
---
name: customer-reply-craft        # 技能 id
name_zh: 售后话术生成              # 中文名（界面显示）
description: 四大售后场景 × 五级情绪安抚策略
version: v1.0
domain: after_sales
priority: P0                       # P0/P1/P2，影响匹配排序
target_agent: generate             # 挂载到哪个 Agent
action_mode: draft                 # read / draft / commit / async_task
requires_confirmation: true        # 受控写入：需人工确认
triggers: [话术, 回复, 怎么回, reply]        # 触发词（权重 3）
discovery_terms: [安抚, 退款, 换货, 政策]   # 发现词（权重 1）
---

## 指令
（Markdown 正文，接模型后作为 system prompt 片段注入）
```

### 内置 6 个技能

| 技能 | 优先级 | 挂载 | 写入模式 |
|---|---|---|---|
| `customer-reply-craft` 售后话术生成 | P0 | generate | 草稿 · **需确认** |
| `after-sales-qa` 售后知识问答与引用 | P0 | retrieve | 只读 |
| `ecommerce-intent-routing` 电商意图识别与工单路由 | P0 | intent | 只读 |
| `emotion-reading` 情绪读空气 | P1 | intent | 只读 |
| `cross-border-escalation` 跨境合规与危机升级 | P1 | compliance | 只读 · **需确认** |
| `offline-fallback` 离线兜底话术 | P2 | generate | 草稿 · **需确认** |

### 触发词机制（为什么要有）

**不是把 6 个技能全量塞进提示词**——那样每次调用都浪费大量 token。
加载器按输入文本匹配 `triggers`(权重3) + `discovery_terms`(权重1)，
只把**本次真正相关**的技能送进管线（默认最多 4 个）。实测：

| 输入 | 命中 |
|---|---|
| 这条裙子到货有污渍，我要退款 | customer-reply-craft, ecommerce-intent-routing |
| 请问这个面料怎么洗 | customer-reply-craft |
| 再不处理我就去平台投诉 | emotion-reading |
| 欧盟客户的退货政策是什么 | after-sales-qa, customer-reply-craft, cross-border-escalation |

命中结果写进 `meta.skills`，并显示在底部**运行日志**里。

### 技能正文注入（v0.7 起已生效）

技能正文**不再只是给模型看的文本**，而是真的在驱动程序行为（三层）：

| 层 | 做什么 | 可验证方式 |
|---|---|---|
| ① 组装提示词 | `基础提示词(5362 字) + 命中技能正文(2409 字) = composed_prompt(7803 字)` | `POST /api/prompt-preview` 或技能中心点「🔍 预览注入后的提示词」 |
| ② 工单路由 + SLA | **解析技能正文里的 Markdown 表格**，按意图查出分派组与 SLA | 分析结果新增「工单路由（技能驱动）」段 |
| ③ 情绪安抚策略 | 解析 `customer-reply-craft.md` 的级别表，按情绪强度选处理方式；**表里写了"主管"就强制升级为高风险** | 分析结果新增「情绪安抚策略（技能驱动）」段 |

**关键：技能 md 是唯一真源。** 改 `ecommerce-intent-routing.md` 表格里的 SLA 值，
分析结果里的 SLA 跟着变；改 `customer-reply-craft.md` 的情绪处理方式，程序行为跟着变。
这就是为什么要写 `Get-SkillMarkdownTable` 把正文表格解析成结构化数据——
否则在没接模型的时候，技能正文就是死的。

分析结果里 `skill_application` 会列出本次每个技能具体贡献了什么。

## 二、界面怎么用

界面上有**四种读取方式**（左侧「读取对话」卡片顶部切换），都汇入同一条处理管线：

| 方式 | 操作 | 准确率 | 适用场景 |
|---|---|---|---|
| **① 窗口直读** | 选一个窗口 → 点「开始自动读取」 | **100%** | **首选**。直接把窗口里的文字读出来，不走 OCR、没有识别误差 |
| **② 剪贴板** | 点「开始监听剪贴板」→ 在任意软件里选中对话按 `Ctrl+C` | **100%** | 最通用。对方不管用什么软件都能用，一次复制即出话术 |
| **③ 读屏 OCR** | 点「开始读屏」→ 选中客服窗口 | ≈95% | 兜底。能读**任何看得见的东西**（包括图片里的字、客户端不暴露文本的界面） |
| **④ 手动输入** | 直接粘进输入框 | 100% | 调试与一次性使用 |

前两种拿到的**是文字本身，不是图片**——没有识别误差，也不消耗视觉模型额度。

> **关于「自动截图」**：本 demo 的读屏**本来就是自动的**（选一次窗口后持续监测，画面一变就分析，不需要你手动截图）。
> 但"自动读文字"比"自动截图再识别"更好，所以做成了现在这样：**能直读就直读，读不了才退到 OCR**。

点「**填充演示样本**」可以一键塞入一段西班牙语投诉，立刻看到完整效果。

生成之后：

**每条候选话术是一个上下分割的双语卡片**（因为我们是面向境外的，客服需要"能直接发出去的"和"自己看得懂的"同时在场）：

```
┌─────────────────────────────────────────┐
│ 安抚致歉   ★推荐   ✓合规通过            │  ← 风格 / 状态标签
├─────────────────────────────────────────┤
│ 发给客户 · English            [复制]     │  ← 上：客户语言，直接发给买家
│ We are very sorry the quality issue...  │
├═════════════════════════════════════════┤  ← 实线分割，一眼看出是两种语言
│ 中文对照                      [复制]     │  ← 下：中文，客服自己核对内容
│ 非常抱歉，这件商品的质量问题给您添麻烦… │
├─────────────────────────────────────────┤
│ [复制话术] [✓采纳] [✎修改后采纳] [✕忽略] │
└─────────────────────────────────────────┘
```

- 上下**各自有独立复制按钮** —— 通常你只复制上面那段发给客户
- 右上角语言选择器决定「上」是哪种语言（英文 / 西语 / 中文）
- 选中文时只显示一块（避免中文重复两遍）
- 目标语言暂时没有对应文案时（如某些风格暂无西语），会**自动回退英文并明确标注**，不会静默给你错的
- **★ 推荐**标记的那条是系统认为最该用的
- 底部 **采纳 / 修改后采纳 / 忽略** 会写进 `logs/qa_logs.jsonl` —— 这就是「数据闭环 Agent」的原料
- 点右上角「**数据闭环**」看采纳率统计

## 三、你提的方案 vs 现在的做法

你说的方案是：**（自动）截图 → 发给 AI → 拿话术 → 复制回对话**。

这个思路**方向完全正确**——先跑通、先上线、先拿到真实反馈，比什么都重要。
但你问"能不能自动读取就更好了"——**能，而且更好**。区别在这里：

| | 自动截图 + 视觉模型 | 自动读文字（本 demo 的①②） |
|---|---|---|
| **原理** | 抓图 → 上传 → 多模态模型看图 → 出文字 → 再分析 | 直接拿到文字 → 分析 |
| **准确率** | 小字/浅色底/外文容易认错，**错一个词话术就跑偏** | **100%**，文字就是文字 |
| **速度** | 要传图、要多模态推理，通常 3~8 秒 | 本地读取 + 文本分析，**不到 1 秒** |
| **成本** | 图片走多模态，token 消耗远高于纯文本 | 极低（甚至零成本） |
| **隐私** | 整张截图（含姓名、地址、旁边窗口）要传到云端 | **文字在本机取，图像根本不离开本机** |
| **缺点** | — | 需要软件暴露文本（见下方限制） |

**所以本 demo 的策略是：能直读就直读，直读不了才用 OCR 兜底。**
三种自动方式（窗口直读 / 剪贴板 / 读屏 OCR）都做了，你可以自己对比。

实测数据（读同一个窗口）：
- 窗口直读：**367 行 / 8818 字，892 ms，零误差**
- 读屏 OCR：258 字，全部识别正确，约 800 ms

## 四、升级路径（这是重点）

这个 demo 的真正价值不是它现在能做什么，而是**它把升级路径铺平了**。四级递进：

```
第 1 级  ★ 你现在的位置：本地规则引擎
         截图/粘贴 → 本机 OCR → 本地规则分析 → 候选话术
         成本 0，不用注册任何账号，离线可跑
                │
                ▼
第 2 级  ★ 接入千帆（下一步）
         把 pipeline.ps1 里的「翻译」和「话术生成」两步换成千帆 API 调用，
         意图识别和合规校验可以保留本地（更快更便宜）
         收益：话术质量从"模板级"跃升到"大模型级"，多语言回译真正可用
                │
                ▼
第 3 级  ★ 剪贴板/快捷键（比截图更好的自动读取）
         听剪贴板或全局快捷键，按一下就读当前选中的对话文本
         收益：准确率 100%（是文字不是图片）、比 OCR 快、token 便宜
                │
                ▼
第 4 级  ★ 浏览器扩展（终极形态）—— 已做出原型，见下一节
         TikTok Shop、Amazon 卖家后台都是网页，扩展直接读页面 DOM，
         侧边栏出话术，一键插入输入框 —— 零复制粘贴
         收益：这是"真接入"，也是申报书里写的最终形态
```

**为什么第 4 级比"对接服务软件"更容易**：跨境电商的客服后台绝大多数是**网页**，
DOM 抓取比逆向桌面客户端容易一个数量级。先做扩展，桌面客户端留到最后。

> 第 3 级（剪贴板）**已经做完了**，就在界面上的「剪贴板」标签页。
> 第 4 级（浏览器扩展）**也已做出原型**，见下一节。

## 四·四、浏览器扩展原型（extension/）

第 4 级做出来了：在客服后台右侧挂一个侧边栏，读对话 → 出话术 → **一键插入输入框**，全程零复制粘贴。

**首选平台：TikTok Shop 商家后台**（申报书的核心用户是服装跨境**直播**商户，主战场就在这）。
Amazon 适配器已占位，后续加平台只需新增一个文件。

### 装起来（3 分钟）

1. 先双击 `启动网页（推荐用扩展，详见README）.bat` 把本地服务跑起来，**窗口别关**
2. 浏览器打开 `edge://extensions/` 或 `chrome://extensions/`
3. 打开右上角「**开发人员模式**」
4. 点「**加载解压缩的扩展**」，选 `hzj-ai-aftersales\extension` 这个**文件夹**
5. 打开 TikTok Shop 商家后台的聊天页 → 右侧自动出现侧边栏

### 首次使用要校准一次（30 秒）

平台的真实 DOM 我无法登录查看，所以扩展默认用**启发式自动识别**找对话区。
如果识别不准，点侧边栏底部 **⚙** → 「拾取消息区」→ 在页面上点一下真正的聊天记录区域
（提示「匹配 N 个元素」，N 等于消息条数就对了）。拾取结果存在本机浏览器里，平台改版后重点一次即可。

### 三种读取方式现在是四层，扩展是最好的一层

| 层级 | 方式 | 需要用户做什么 |
|---|---|---|
| ①② | 窗口直读 / 剪贴板 | 桌面演示版，选窗口或按 Ctrl+C |
| ③ | 读屏 OCR | 兜底 |
| **④** | **浏览器扩展** | **什么都不用做** —— 页面一变就自动分析，点一下插入输入框 |

### 扩展的安全设计

| 项 | 做法 |
|---|---|
| **密钥不进浏览器** | 扩展完全不接触 API Key，只调本地服务；密钥用 DPAPI 存在本地 |
| **请求由 Service Worker 发** | 内容脚本 fetch 会带宿主页面 Origin，本地服务就得对任意网站开放跨域（等于让所有网页都能读你的剪贴板）。改由扩展发请求，Origin 是 `chrome-extension://` |
| **本地服务 CORS 已收紧** | 从 `Access-Control-Allow-Origin: *` 改成白名单：只放行扩展和本机页面。实测 TikTok 页面、任意网站都被拒 |
| **永不自动发送** | 扩展只**插入**输入框，绝不替你点发送 —— 人工确认后才发 |

### 我需要你提供什么

详见 `extension/README.md` 第三节。最有用的是**真实对话区的 HTML 片段**（F12 → 选中消息容器 → Copy outerHTML，记得脱敏），
有了它我就能把"未验证的选择器"换成准确选择器。**不给也能用**，靠拾取器现场学。

## 四·五、接模型：接口已留好，密钥已解决

现在**默认不调用任何外部模型**，走本地规则引擎。接模型只需要三步，`pipeline.ps1` 一行都不用改。

### 第 1 步：配置

复制 `config.example.json` 为 `config.local.json`（已被 git 忽略），改两处：

```json
{ "model": { "provider": "qianfan", "endpoint": "控制台复制的调用地址", "model": "ernie-4.5" } }
```

### 第 2 步：存密钥（安全的关键）

```powershell
powershell -ExecutionPolicy Bypass -File tools\set-api-key.ps1
```

输入密钥时**屏幕不回显**。它会做这些事：

| 措施 | 说明 |
|---|---|
| **DPAPI 加密** | 用 Windows 数据保护 API 加密，绑定**当前 Windows 账号**。把密文拷到别的电脑或别的账号下**解不开**，等于废纸 |
| **不放在仓库里** | 优先存 `%APPDATA%\hzj-agent\`；该位置不可写时才退到 `hzj-ai-aftersales\.secrets\`（同样加密，且被 `.gitignore` 挡死） |
| **永不返回前端** | 所有 HTTP 接口只返回 `has_key: true/false` 和 8 位指纹，**没有任何接口能取回密钥本身** |
| **日志脱敏（v0.33.0 起）** | 请求体落盘前过 `Protect-LogBody`：密钥整值抹掉、正文只留长度。**v0.33.0 之前没有这一层**，密钥和客户对话原文确实进过 `logs\requests.log`，已修并删除存量日志 |
| **只暴露指纹** | `tools\set-api-key.ps1 -Status` 显示 SHA256 前 8 位，够你确认"是不是我存的那把"，但推不出密钥 |

## 五、做网页还是做软件？

**结论：做网页（Web 应用），不做桌面软件。** 具体形态是「**本地 Web 服务 + 浏览器界面**」：

```
浏览器界面（web/）
      │  HTTP → 127.0.0.1:8799
      ▼
本地服务（server.ps1：静态文件 + /api/analyze + /api/ocr + /api/feedback）
      │
      ▼
引擎（engine/：OCR · 知识库 · 7-Agent 管线）
```

注意它**不是"一个 html 文件"**，必须有后端。因为：

1. **密钥安全**：千帆的 API Key 绝不能放在浏览器里。纯前端网页一发布，任何人按 F12 就能拿走你的密钥刷你的额度。
2. **跨域限制**：浏览器直连千帆 API 会被 CORS 拦截，必须由本地服务中转。
3. **本地能力**：Windows OCR 只能在本地调，浏览器做不到。

**为什么是网页而不是桌面软件**：

| 理由 | 说明 |
|---|---|
| 与申报书一致 | 申报书 4.1 写的就是「轻量化 Web 坐席客服工作台，适配电脑端快速操作」 |
| 切中真实痛点 | 申报书 2.2 列了「中小商户数字化接受度偏低」——让商户**下载安装一个 exe** 是巨大阻力，发个链接就能用才是零门槛 |
| 商业模式要求 | 申报书 6.2 是 SaaS 订阅 + 按效付费 + 政企推广。**SaaS 只能是 Web**，桌面软件没法按坐席订阅 |
| 升级平滑 | 开发期跑在 `127.0.0.1`，将来把 server.ps1 搬到云上就是完整 SaaS，前端一行不用改 |

将来如果确实需要桌面版，按申报书 1.3 的定位，用 **DuMate 做轻量化桌面辅助插件**作为补充，而不是主路径。

判读方法：如果某列 `scrollHeight > clientHeight` 但 `overflow-y` 不是 `auto/scroll`，

| 抓到的缺陷 | 后果 | 修法 |
|---|---|---|
| 规则 R018/R019（欧盟14天告知、德国撤回权）误写成违规型正则 | **任何提到"退货/退款"的合规话术都会被误杀，误杀率 100%** | 引入 `match_mode`：`violation`（正则可靠）vs `obligation`（只能模型判） |

## 八、已知限制（都是有意为之，不是 bug）

| 限制 | 说明 | 解决路径 |
|---|---|---|
| **窗口直读依赖软件暴露文本** | 桌面客户端和浏览器通常都暴露（实测读一个窗口拿到 367 行/8818 字），但个别自绘 UI 的软件不暴露 | 退到「剪贴板」或「读屏 OCR」；网页类后台最终用**浏览器扩展**最稳 |
| **窗口直读会读到界面文字** | 窗口标题、按钮文字（如「最小化」「关闭」）也会被读出来 | 策略上已优先只读「文档区」以避开工具栏；残留的杂行可在输入框删掉 |
| **剪贴板每次要按 Ctrl+C** | 不能完全零操作 | 下一步可做**全局快捷键**（按一下自动复制+分析），或直接上浏览器扩展 |
| **OCR 会读到界面文字** | 同窗口直读 | 同上，可在输入框删掉多余行 |
| **多语言 OCR 只支持中/英** | 本机装了 `en-US` 和 `zh-Hans-CN` 语言包。西/德/法文字靠英文引擎勉强识别 | 在 Windows「语言和区域」里安装对应语言包即可，装完重启服务自动生效。**注意：只有 OCR 受此限制，窗口直读和剪贴板不受影响** |
| **OCR 语言是"择优"不是"合并"** | 中英混排的截图会挑一个字多的语言跑 | 升级为多语言结果合并去重 |
| **话术模板是固定文案** | 14 个意图 × 3 风格，不支持任意品类/场景 | 接千帆话术生成 Agent（接口已留好） |
| **西语候选话术覆盖不全** | 只有部分模板带西语，其余回退英文并给提示 | 接千帆翻译 Agent 自动回译 |
| **千帆接口字段未验证** | 适配器按通用 Chat Completions 格式写，未对照千帆实际文档核实 | 跑 `tools\test-model.ps1 -DryRun` 核对后再上线 |

## 十、改代码前必读（踩过的坑）

**⚠️ 编辑 `*.ps1` 后必须把文件存成「UTF-8 带 BOM」。**

PowerShell 5.1 读取 `.ps1` 时，如果文件没有 BOM，会按系统 ANSI 代码页解析。
中文会变成乱码，进而**破坏字符串引号配对，导致整脚本语法错误**：

```
+   Write-Host ("  Windows OCR 鍙敤璇█锛? + ($ocrLangs -join ', '))
Unexpected token 'Windows' in expression or statement.
```

救急命令：

```powershell
$b = New-Object System.Text.UTF8Encoding($true)
Get-ChildItem -Recurse -Filter *.ps1 . | ForEach-Object {
  $t = [System.IO.File]::ReadAllText($_.FullName, (New-Object System.Text.UTF8Encoding($false)))
  [System.IO.File]::WriteAllText($_.FullName, $t, $b)
}
```

HTML / CSS / JS / CSV **不需要** BOM —— 它们的编码由 HTTP 头或 `-Encoding UTF8` 显式指定。
